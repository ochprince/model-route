# 设计笔记

影响设计的实测记录。它们放在这里而不是 README 里，免得产品文档读起来像变更日志。
每条都记录了观察的时间和范围——这些是单台机器上的观察，不是受控实验。

## 回合内重判信号（2026-10，单机）

**问题。** 回合内条件变化时，网关该不该重新判定——工具结果失败、累计工具调用数、上下文大幅增长？

**怎么测的。** 网关把每次决策的来源与触发边界写进日志。在一台机器约两周的日常使用中收集到 194 条决策，其中三类回合内信号共触发 14 次。

**结果。**

| 信号 | 触发次数 | 改变档位 | 判定耗时 |
| --- | --- | --- | --- |
| 累计工具结果（每 8 个） | 10 | 0 | 13.2 秒 |
| 工具结果失败 | 3 | 0 | 约 3 秒 |
| 上下文增长（60k 字符） | 1 | 0 | 约 1 秒 |
| 历史重建 | 0 | 0 | — |

每次触发得到的档位，都和这个回合原本在跑的档位相同。那些回合里唯一一次档位变化，来自当时存在的跨回合升档规则，不是回合内信号。

**原因。** 这些信号描述的是规模，不是难度：跑了八次工具调用之后，判定模型当初分类的那个请求并没有变，变的只是它背后的工作量。而且触发点恰是最贵的时候——上下文最大，换档要重建最大的那段前缀。

**决定。** 去掉这三类回合内信号；只保留「历史重建」作为唯一的回合内重判，因为压缩替换掉了冻结决策所依据的上下文，那个决策无法继承。

**局限。** 单机、单套 provider、单一判定模型，样本也小（14 次触发）。换一种工作负载完全可能得到不同数字；能推广的是上面的机制论证，计数只是例证。

## 判定请求体的构成（2026-10，单机）

**问题。** 判定模型该看到什么？

**观察。** 第一版发送最近的对话，每条消息统一按字符数截断、不区分角色。在一个真实的长回合里（6 个历史回合 + 本轮 3 次工具往返），请求体约 2% 是用户文本、72% 是助手文本——助手回复本来就比用户消息长，而两者被截到同样长度。

**决定。** 只发判定所需：当前请求、更早的用户消息、上一轮档位。助手输出、工具流量、Agent 系统提示词、派生标志全部去掉。

**局限。** 这些百分比描述的是那一种请求体形状，不是所有会话的普遍性质。

## 确定性升档地板（2026-10 移除）

**它是什么。** 用正则扫最近的用户回合，命中否定措辞（「还是不对」「没修好」……）就强制至少比上一轮高一档，覆盖判定模型的结论。

**为什么移除。** 同一份正则结果既作为证据给了判定模型，又作为指令写进了提示词，地板等于把模型刚做过的判断再执行一遍——而且在模型不同意时推翻它。它还会命中「被否定的对象根本不是模型回答」的措辞：一句包含「刷新按钮没有效果」的消息被读成“上一轮被否决”，于是把该轮抬到最强档。

**决定。** 删掉地板。判定结果即最终档位；判定调用失败则回落到 `fallbackTier`。识别否定的能力放进提示词，那里能用整段对话，而不是一个子串。
